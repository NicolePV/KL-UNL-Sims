# Conversion Notes — Sun's Position on Horizon

Source: `horizon.swf` (Flash 6 / ActionScript 1, stage 680 × 268).
Target: self-contained HTML5 on the KL-UNL foundation, `sim-id` = `horizon`.

## Behaviour model

The simulation shows the view toward the horizon from a fixed northern-hemisphere
landscape — east at sunrise, or west at sunset — and animates where along that
horizon the sun comes up (or goes down) as the year passes. A day counter
`_day` runs 0–365 and drives a single offset, `sin(2π · day / 365)`, which is
zero at the equinoxes and ±1 at the solstices. The sun graphic, with the date
label riding above it, is placed at `x = ±350 × offset`, negated for the sunrise
view so that the sun drifts toward the *north* end of the horizon in northern
summer and toward the *south* end in winter. Seven foreground objects (two
bushes, a house and four trees) each carry a 366-frame shadow clip; the frame
shown is `184 − floor(offset × 91)`, so every shadow shears away from the sun as
it moves along the horizon. Pressing Play advances `_day` by `0.025` per
millisecond of elapsed wall-clock time — one full year every 14.6 seconds —
wrapping at 365. The two radio buttons switch between the sunrise and sunset
views, which swaps the sky gradient, mirrors the whole landscape, swaps the
"To North" / "To South" end labels, and rewrites the caption.

## ActionScript → HTML5 mapping

| `monthArray` (12 pushes) | `MONTH_TABLE`, day counts verbatim |
| `dateArray` + 80 × `push(shift())` | `DATE_ARRAY`, same rotation |
| `p.getOffsetAt` | `getOffsetAt()`, formula unchanged |
| `p.moveSunTo` | the `moveSunTo` block inside `render()` |
| `p.setType` / `p.setDay` / `p.setAnimate` | `setType()` / `setDay()` / `setAnimate()` |
| `p.onEnterFrame` + `getTimer()` | `tick()` on `requestAnimationFrame` + `performance.now()` |
| `_range = 350`, `_speed = 0.025`, `_anim = false` | `RANGE`, `SPEED`, `state.animating` |

Constants, the month table, the date-array rotation, the offset formula, the
shadow-frame formula, the timing constants and every on-screen string are
verbatim from the source.

## Assets: reused, not redrawn

The SWF contains no code-drawn art — there is not a single
`createEmptyMovieClip` / `beginFill` / `drawArc` call. Every visual element is
an exported vector shape, so all 21 shapes the simulation uses are reused
exactly as JPEXS exported them:

* `assets/shapes/*.svg` — the untouched exports, kept for provenance.
* `assets/scene-data.js` — generated by `assets/build_assets.py`, which copies
  each shape's `<path>` and gradient markup **verbatim** into one shared
  document (only element ids are namespaced, since every export reuses
  `gradient0`, `gradient1`, …) and pairs them with the display lists and
  matrices read out of the SWF's own `PlaceObject2` tags.

Shape roles: `78`/`79`/`107` sky, `80` ground band, `82`–`94` trees, bushes and
their shadows, `90`/`96`–`100` house parts, `101`/`102`/`108` direction arrows,
`72`/`76` sun glow.

### Rendering architecture: inline SVG rather than canvas

The pipeline brief specifies a `<canvas>` stage for "the code-drawn art and
animation … orbits, electrons, photons, energy bars, masks". This simulation has
none of that category; 100 % of its artwork is exported vector shapes, which the
same brief says to reuse as-is via "inline `<svg>`, `<img>`, or `drawImage` of
the SVG". Inline SVG was chosen because it:

* reuses the exported files literally, with no rasterisation step;
* stays sharp at any zoom level, which matters for WCAG 1.4.4 / 1.4.10 —
  `drawImage` of an SVG rasterises at the intrinsic size in Chrome, so a canvas
  stage would visibly soften on high-DPI displays and at 200 % zoom;
* lets the direction labels and the date be *real text* rather than pixels;
* expresses the shadow shear and the sun's travel as exact matrix transforms.

The stage keeps the original internal coordinate system (the `sun_Gradient`
clip's local space, `x ∈ [−425, 425]`, `y ∈ [−275, 60]`) via `viewBox`, and CSS
scales it. No drawing or physics maths was recomputed from the on-screen size.

### Colour transforms

Every landscape placement in the SWF carries a `CXFORM` colour transform — this
is what renders the full-colour authoring artwork as dark silhouettes, and what
draws the direction arrows at half opacity. These are reproduced exactly as
`feColorMatrix` filters (`out = clamp(in × mult / 256 + add)`), deduplicated to
eight filters. `color-interpolation-filters="sRGB"` is set because the SVG
default of linearRGB would tint the result differently from Flash.

### Verification

Rendered at the native 680 × 268 and compared pixel-for-pixel against the SWF's
own frame export (`frames/1.png`), excluding the text and the two widgets that
became native controls: **mean absolute difference 2.1 / 255**, with the only
differences above 20 being one-pixel anti-aliasing edges (median 3 neighbouring
differing pixels — thin outlines, not areas). The artwork is a faithful
reproduction.

## Deviations from the original

1. **Initial date.** The authored first frame showed a hard-coded placeholder,
   "September 21", while `_day` was initialised to `0` — which is *March 21*.
   The two never agreed: the original only started showing real dates on the
   first animation tick. The port renders from state on load, so it opens on
   March 21 with the sun, the date and the shadows mutually consistent. Both
   dates are equinoxes with an offset of ~0, so the picture is unchanged; only
   the label differs. Reset returns to this same March 21 state.

2. **Date controls were added: a slider, plus a month/day entry.** The original
   could only play and pause — there was no way to examine a particular date,
   which leaves keyboard and screen-reader users unable to explore the
   simulation at all, and no way for anyone to jump to a date of interest such
   as a solstice. Both controls drive `setDay()`, an entry point the
   ActionScript class already defined but never wired to any control, and the
   month/day pair resolves a typed date by looking it up in the same
   `dateArray` the scene renders from, so the two cannot diverge. The day is
   clamped to the selected month's length using the source's own month table
   (February = 29). No physics changed.

3. **The caption moved out of the artwork.** `descTextField` was white text
   painted on the pale sky, about 2.2:1 contrast. It is now an HTML paragraph
   above the scene in the foundation's text colour. See `ACCESSIBILITY.md`.

4. **Direction labels gained a dark halo.** Same contrast problem, but these
   labels have to stay anchored to the horizon, so they keep the original white
   script face over a dark outline instead of moving. See `ACCESSIBILITY.md`.

5. **Flash UI components were not ported.** `mx.controls.RadioButton`,
   `mx.controls.Button` and the focus-manager machinery are replaced by native
   labelled controls, per the brief.

6. **Animation clock is clamped.** Flash ran `onEnterFrame` continuously, so its
   single `_day -= 365` wrap was always sufficient. A browser suspends
   `requestAnimationFrame` entirely while a tab is hidden, which would hand the
   next tick a gap of many seconds and push `_day` past the end of `dateArray`.
   The elapsed step is therefore capped at one year, and the clock restarts on
   `visibilitychange`, so returning to a backgrounded tab resumes where the
   reader left off instead of jumping. Within a normal frame interval this is
   bit-identical to the original.

## No mathematics is displayed

The pipeline requires every mathematical symbol or expression shown to the user
to be typeset by MathJax. This simulation displays no mathematics: its only
readouts are calendar dates ("March 21") and prose. The underlying
`sin(2π · day / 365)` is internal and was never surfaced by the original, and
adding it would introduce teaching content the original did not have. There is
accordingly nothing to typeset, and no MathJax include is present in this
project's `foundation/` folder. `foundation/kl-unl.js` is still linked and
`klunlInitEqn()` is redefined by `simulation.js` to initialise the simulation,
which is the hook the foundation provides for exactly this purpose.

## Cross-browser notes

Everything used is broadly supported: inline SVG, `feColorMatrix`, CSS grid,
`<details>`, Pointer-Events-free native controls, ES modules. No vendor-prefixed
property is used as a sole declaration and there are no Chrome-only APIs.
`paint-order` (used for the text halos) is supported in Chrome, Edge, Firefox
and Safari; where it were ever unsupported the text still renders, just with the
stroke over the fill rather than under it — legible either way.

## Foundation observation (not modified)

`foundation/kl-unl.css` line 101 contains a stray `u` between the
`.app-layout__left` and `.app-layout__right` rule blocks, which turns the latter
into a `u .app-layout__right` descendant selector, so `.app-layout__right`'s
`min-width: 0` never applies. This sim sets its own `min-width: 0` in
`styles/styles.css` instead. The foundation file was **not** edited — flagging
it here for whoever maintains the shared files.
